# 方法说明：为什么这样生成测试盘，又怎样保证公平

这份文档解释三件事：

1. 为什么不直接扫真实硬盘，而用合成数据；
2. 合成数据的生成算法每一部分是为了什么，怎样模仿一块用了多年的盘；
3. 跑分、判罚和计分怎样尽量公平，以及还有哪些已知局限。

---

## 1. 为什么用合成数据

| 要求 | 真实硬盘做不到的地方 | 合成数据怎么做 |
| :--- | :--- | :--- |
| **每次都扫同一棵树** | 每台机器、每天的内容都不一样 | 目录树完全由种子（`--seed`，ChaCha8 随机数）决定，同一种子在所有平台、所有运行里一模一样 |
| **规模可控** | 想测 100 万、900 万文件就得有那么大的盘 | 6 个预设体量（10 万 ~ 900 万文件），也可自定义 |
| **能在免费 CI 上跑** | runner 只有几十 GB 磁盘 | 大文件只分配不写数据，逻辑上几 TB 的卷，物理上只占几 GB |
| **知道标准答案** | 没人知道一块真实盘"应该"有多大 | 生成器同时写出 `ground_truth.json`：文件数、目录数、逻辑大小、实际占用、每个顶层区域的明细 |
| **不泄露隐私** | 真实盘的文件名、路径属于个人信息 | 合成名字；需要模仿某块真实盘时只用不含任何名字的统计直方图（见 §2.4） |

合成数据的风险是**"不像真的"**：某个扫描器可能恰好擅长合成数据里的某种结构，在真实盘上却没有这个优势（我们称为"结构性逃逸"）。下面每一条设计都在尽量堵住这种偏差。

---

## 2. 生成算法

### 2.1 四个区域：覆盖真实盘的典型结构和陷阱

| 区域 | 模仿什么 | 考验扫描器什么 |
| :--- | :--- | :--- |
| `zone_deep` | 依赖目录（`node_modules`、包缓存）：8–25 层的深链，每层很少的文件 | 目录打开次数、递归深度、路径拼接 |
| `zone_flat_cache` | 浏览器 / 构建缓存：少数目录里塞几千个文件 | 大目录的批量枚举 |
| `zone_sparse_media` | 视频、镜像、虚拟机磁盘：少量超大文件，外加几个比卷还大的稀疏"空洞"文件 | 大文件的占用计算、稀疏文件是否算对 |
| `zone_edge` | 硬链接、符号链接循环、超长路径 | 硬链接是否重复计数、遇到链接循环会不会卡死、长路径会不会出错 |

### 2.2 文件大小和实际占用：像真的，但不占物理空间

真实盘上几乎没有稀疏文件，所以合成数据也尽量不用稀疏文件。只有体积大到写不下的文件才例外：

- **很小的文件**（不超过 680 字节）：NTFS 上直接放进 MFT 记录，和真实小文件一样。
- **普通文件**：用 `SetEndOfFile`（Windows）分配空间但不写数据。文件系统真的给它分配了簇，扫描器读到的"占用大小"是真实的，但不需要真的写这么多数据。
- **部分文件写入几个 4 KiB 的"锚点"块**：让文件里有真实的数据段，而不是全空。
- **大文件**（256 KiB 以上）：预分配（Windows 用 `SetEndOfFile`，Linux 用 `fallocate`），不写数据。
- **在 Linux / macOS 上**，没有数据的文件是空洞（不占块）。Unix 上的扫描器本来就要对每个文件调用 `stat`，所以空洞不会让某个扫描器多做额外工作。

> 为什么要专门处理稀疏？早期版本里小文件都是稀疏的。会精确计算稀疏文件占用的扫描器（比如 SpaceKnife、WinDirStat）就得对每个稀疏文件单独打开查询，在合成数据上白白慢了好几倍；而真实盘上几乎没有稀疏文件，这就是一种不公平。现在只有确实需要的地方才稀疏。

### 2.3 老化：模仿一块用了多年的盘（`FSM_AGING=1`）

一块刚格式化、按目录顺序一口气写满的卷，和一块用了几年的卷，在磁盘上的布局完全不同：

- **新卷**：所有目录的记录（NTFS 的 MFT 记录 / ext4 的 inode）挤在一起，每个目录的文件记录连成一片，目录索引一次就长到最终大小。冷扫时，读一块就能顺带读到一大串有用的记录，比真实盘便宜好几倍。
- **旧卷**：目录和文件是在几年里陆续创建的，记录东一块西一块，目录索引一点一点长大、分散在多处，中间还夹着已删除文件留下的空洞。

如果只用新卷测，冷扫成绩会偏向那些恰好受益于"记录连续"的读盘方式。所以生成器有一个"老化时间线"：

1. **目录出生时间**：每个目录在父目录之后的某个随机时间点被创建。
2. **文件分批到达**：每个目录的文件被拆成 4–64 个一批的"突发"，分散在目录出生之后的整条时间线上。
3. **按时间线执行**：所有目录创建和文件批次按时间排序后执行（每 8192 个任务一个窗口，窗口内并行）。结果是目录记录和文件记录交错，每个目录的索引分多次增长。
4. **删改痕迹（churn）**：大约每 8 个文件旁边会创建一个临时文件再删除。临时文件真的分配了空间，删除后留下空洞和可复用的记录，就像日常使用中的临时文件、下载缓存。
5. **目录内顺序打乱**：同一目录里的文件按确定性的随机顺序创建（由目录名做种子），而不是按名字顺序，避免"名字顺序 = 磁盘顺序"这种真实盘上不存在的巧合。

CI 的 Windows 任务默认开启老化（工作流输入 `windows_aging`）。所有这些步骤都由种子决定，同一种子每次生成的布局完全一样。

### 2.4 用真实盘的画像生成同形状的树（`--profile`）

`scripts/profile/fs_profile.py` 可以对一块真实盘做统计，只输出直方图：目录深度分布、每个目录装多少文件和子目录（按深度分组）、文件大小分布、文件名和扩展名长度、字符种类占比、属性占比。**不含任何文件名、目录名或路径。**

`fs-mirage --profile <画像>.json` 按这些直方图生成一棵形状相同的树。这样可以检查"在合成数据上的名次"和"在这种真实结构上的名次"是否一致，用来发现结构性逃逸。

## 3. 跑分怎样尽量公平

| 环节 | 做法 | 为什么 |
| :--- | :--- | :--- |
| **同一台机器、同一份数据** | 每个平台的所有扫描器在同一个 runner 上依次扫同一个卷 | 消除机器差异 |
| **真正的冷扫** | 每次冷扫前卸载并重新挂载虚拟盘（Windows VHDX、Linux 直接 I/O 的 loop 设备、macOS 磁盘镜像），Linux 再清页缓存 | 冷扫必须从盘上读，不能读到缓存 |
| **冷扫是进程第二次启动** | 计时前先在一个小目录上跑一遍真实扫描命令（不计时） | 第一次启动要付的杀毒扫描、DLL 加载、运行时解压不该算进扫描时间 |
| **热扫取多次** | 冷扫之后连续热扫多次取平均 | 降低偶然波动 |
| **杀毒** | 默认关闭 Defender 实时防护并排除测试盘；`defender_scan` 输入可以只在扫描阶段打开它做对照 | 实测打开 Defender 对所有扫描器都没有可见影响 |
| **线程** | 各扫描器使用默认设置；CI runner 是 4 个逻辑核 | 反映用户开箱即用的表现；CI 成绩相当于一台 4 核电脑 |
| **结果正确性** | 每个扫描器的文件数、总大小、顶层区域大小都和标准答案比对；遍历不完整或越界的成绩判为无效 | 快但算错不算数 |

### 3.1 MFT 逃逸判罚

直接读 NTFS `$MFT` 的扫描器会在 NTFS 上快得多，但这不是"遍历目录"的能力。普通跑分里所有扫描器都被要求走标准目录遍历；读 MFT 的模式在单独的 **MFT 专栏**里比较。

为了发现偷偷读 MFT 的情况，同一份数据会在 NTFS 和 ReFS（没有 MFT）上各跑一次。只有**两个迹象同时出现**才判 MFT 逃逸：

1. ReFS 对它明显比对其他扫描器慢（ReFS/NTFS 耗时比超过所有扫描器中位数的 2 倍）；
2. 它在 NTFS 上冷扫和热扫几乎一样快（冷扫/热扫 ≤ 1.3 倍）——读 MFT 每次都要读完整张表，冷热没有区别。

只满足第 1 条的扫描器只是"在 ReFS 上偏慢"（例如每个文件都要单独查询的工具），会在核查表里标出，但不处罚。被判逃逸时只取消 NTFS 成绩；ReFS 上不存在 MFT，那份成绩照常有效。

### 3.2 小体量只作参考

`very-lite`（10 万文件）和 `lite`（40 万文件）的扫描只需零点几秒到几秒。榜单计的是**进程从启动到退出的总墙钟时间**，不是软件自己报告的扫描时间，体量越小，启动和初始化的固定开销占比越大。这两个体量的榜单都带有"仅供参考"声明，也不计入跨体量综合分。

## 4. 计分

**单个平台内**：先算相对分，硬件快慢在这一步就约掉了。

- 冷扫分 = 该平台最快冷扫时间 ÷ 本扫描器冷扫时间 × 100
- 热扫分 = 同理
- 均衡指数分 = 本扫描器均衡指数 ÷ 该平台最高均衡指数 × 100（冷热取几何平均）

**均衡指数**同时考虑墙钟时间和占用的资源：

- $T_{\text{cpu}} = C/P$：进程树的 CPU 时间摊到所有逻辑核；
- $T_{\text{io}} = Q/S_{\text{IOPS}}$：它造成的设备读次数，按该平台测得的随机读上限折算；
- $M = T_{\text{cpu}} + T_{\text{io}}$，$B = T_{\text{wall}}^{0.5} \cdot M^{0.5}$，得分 $= N_{\text{items}}/B$。

跑得快但把 CPU 和磁盘压得更满的扫描器，均衡指数不会因此占便宜。

**跨平台**：每项相对分在扫描器有效的平台上取几何平均；综合分 = 冷扫、热扫、均衡三项的几何平均。

**跨体量**：综合分只取 `low` 及以上体量的几何平均。

## 5. 已知局限

- **CI 的磁盘是云盘**：随机读上限只有几千到一万多次每秒，顺序读相对便宜；本地 NVMe 的特性完全不同。冷扫在 CI 上更像"慢盘场景"。
- **CI 只有 4 个逻辑核**：能随核数扩展的扫描器在桌面多核机器上会更快，CI 成绩体现不出来。
- **macOS 冷扫不够冷**：磁盘镜像的缓存清理不彻底，macOS 的冷扫成绩接近热扫。
- **导出模式的开销**：部分图形界面工具只能用"导出到文件"的方式无界面运行（例如 WinDirStat `/SaveTo` 会写出每一项的 CSV），这部分时间也算在成绩里。
- **大小口径不同**：有的工具只报告逻辑大小，有的报告实际占用，有的不对硬链接去重。准确度一列按各自的口径分别对照标准答案。

如果发现某个扫描器在合成数据上的排名和真实盘明显不一致，欢迎用本地基准套件提交真实盘的成绩做对照。
